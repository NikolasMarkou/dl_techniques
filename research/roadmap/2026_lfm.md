# Liquid Foundation Models (LFM) — Architecture, Parameters & Technology

> Research document compiled from public sources (Liquid AI blog, technical reports, Hugging Face model cards, arXiv papers) as of 2026-10-14.

---

## 1. Overview

**Liquid Foundation Models (LFMs)** are a family of **non-transformer** generative AI models developed by **Liquid AI** (MIT CSAIL spin-off). They are built from **adaptive linear operators** grounded in:

- **Dynamical systems theory**
- **Signal processing**
- **Numerical linear algebra**

**Design goal**: "Explore ways to build foundation models beyond Generative Pre-trained Transformers (GPTs)" — from first principles, the way engineers build engines.

**Key claim**: State-of-the-art quality at each parameter scale with **smaller memory footprint** and **more efficient inference** vs. transformer baselines.

## 3. Architecture

### 3.1 Core Design Philosophy

> **Edge-first**: Co-design architecture, pre-training, and post-training around **device-side latency and peak memory constraints** (CPU, NPU, heterogeneous SoCs).

> **Hardware-in-the-loop architecture search**: Search space evaluated by measuring **real inference speed and peak memory** on target hardware (Qualcomm Snapdragon, Apple Silicon, etc.), not FLOPs proxies.

### 3.2 LFM2 / LFM2.5 Backbone (Minimal Hybrid)

Selected by hardware-in-the-loop search as the **Pareto-optimal** combination under edge budgets:

```
┌─────────────────────────────────────────────────────────────────┐
│                      LFM2 BLOCK (per layer)                     │
├─────────────────────────────────────────────────────────────────┤
│  Pre-norm RMSNorm                                               │
│       │                                                         │
│       ├──► Local Context Block (majority)                       │
│       │     └─ Gated Short Convolution (LIV / double-gated)     │
│       │           • Depthwise, kernel k=3                       │
│       │           • Input-dependent multiplicative gates        │
│       │           • Conv bias: False, L_cache=3                 │
│       │                                                         │
│       └──► Global Context Block (minority)                      │
│             └─ Grouped-Query Attention (GQA)                    │
│                   • QK-Norm (Dehghani et al., 2023)             │
│                   • RoPE (Su et al., 2024)                      │
│                   • Head dim = 64, KV groups = 8                │
│                                                                 │
│  Position-wise: SwiGLU FFN (Shazeer, 2020)                      │
│       • Expansion ratio set by search                           │
│       • block_multiple_of=256, block_ffn_dim_multiplier=1.0     │
└─────────────────────────────────────────────────────────────────┘
```

**Why this hybrid?**
- Search considered: SSMs (Mamba, S4, Liquid-S4), linear attention, sliding-window attention, full hybrids (conv + SSM)
- **Finding**: Under real edge latency/memory budgets, a **minimal hybrid** (gated short conv + sparse GQA) suffices — no separate SSM/linear-attention operators needed.
- Short convolutions: optimized for embedded SoC CPUs, 2× faster decode/prefill vs. similar-sized transformers.

### 3.3 Layer Layout (Dense Models)

| Model | Total Layers | Conv Blocks | Attention Blocks | Pattern |
|-------|-------------|-------------|------------------|---------|
| 350M | 16 | 10 | 6 | 10 conv + 6 attn |
| 700M | 16 | 10 | 6 | 10 conv + 6 attn |
| 1.2B | 16 | 10 | 6 | 10 conv + 6 attn |
| 2.6B | 30 | 22 | 8 | 22 conv + 8 attn |

### 3.4 MoE Extension (LFM2-8B-A1B, LFM2.5-24B-A2B)

- **Backbone**: Same hybrid conv/GQA
- **MLP replacement**: Dense SwiGLU → **Sparse MoE SwiGLU** (per layer)
- **Routing**: Normalized sigmoid router + adaptive routing biases (Liu et al., 2024)
- **Stability**: First 2 layers remain dense; all subsequent layers MoE

| Model | Total / Active | Layers | Experts/Layer | Top-k | Expert FF Dim |
|-------|---------------|--------|---------------|-------|---------------|
| LFM2-8B-A1B | 8.3B / 1.5B | 24 | 32 | 4 | 1792 |
| LFM2.5-24B-A2B | ~24B / ~2B | — | — | — | — |

### 3.5 LFM1 Architecture (First Gen)

- Custom computational units in **depth groups** (targeted weight sharing)
- **Featurizer interconnections** (feature sharing across groups)
- Design space: **featurization** × **operator footprint**
- Operators: adaptive linear operators modulated by input features
- Unified token-mixing, channel-mixing, featurization

## 5. Configuration Reference (Lfm2Config)

```python
# From transformers Lfm2Config (defaults ≈ LFM2-1.2B)
vocab_size: 65536
hidden_size: 2560          # d_model
intermediate_size: 12288   # FF dim
num_hidden_layers: 32
num_attention_heads: 32
num_key_value_heads: 8     # GQA groups
max_position_embeddings: 128000  # RoPE max (but trained on 32K)
initializer_range: 0.02
norm_eps: 1e-5
use_cache: True
pad_token_id: 0
bos_token_id: 1
eos_token_id: 2
tie_word_embeddings: True
rope_parameters: {rope_theta: ...}
conv_bias: False
conv_L_cache: 3
block_multiple_of: 256
block_ffn_dim_multiplier: 1.0
block_auto_adjust_ff_dim: True
full_attn_idxs: []         # Indices of attention layers
layer_types: []            # Explicit per-layer type: "conv" or "attention"
```

> **Note**: The HF config defaults (32 layers, 2560 hidden) differ from the released dense checkpoints (16 layers, varying hidden). The released models use explicit `layer_types` and `full_attn_idxs` to define the hybrid layout.

## 6. Technology & Deployment

### 6.1 Training
- **Data**: 10 trillion tokens (LFM2), diverse multilingual + code + math
- **Precision**: bfloat16
- **Context**: 32,768 tokens (trained), RoPE supports up to 128K
- **Speed**: 3× faster training vs. LFM1 generation

### 6.2 Inference Efficiency
| Metric | Claim |
|--------|-------|
| Prefill speed (CPU) | 2× faster vs. Qwen3 same size |
| Decode speed (CPU) | 2× faster vs. Qwen3 same size |
| Memory footprint | Sub-linear KV cache growth → long context on device |
| Peak memory | Optimized via architecture search for target SoCs |

### 6.3 Supported Runtimes / Formats
| Runtime | Status |
|---------|--------|
| **Transformers (HF)** | ✅ Native `Lfm2ForCausalLM` |
| **llama.cpp** | ✅ GGUF quantized variants |
| **ExecuTorch** | ✅ On-device mobile/edge |
| **vLLM** | ✅ High-throughput serving |
| **MLX** | ✅ Apple Silicon |
| **ONNX** | ✅ Cross-platform |
| **GGUF** | ✅ Quantized (4-bit, 8-bit, etc.) |

### 6.4 Quantization
- Pre-quantized GGUF variants for edge runtimes
- bfloat16 native; INT4/INT8 via llama.cpp / ExecuTorch quantization

## 8. Key Innovations Summary

| Innovation | Description |
|------------|-------------|
| **Adaptive linear operators** | Operators = linear maps modulated by input-dependent gates (dynamical systems view) |
| **Gated short convolutions** | Depthwise k=3 conv with multiplicative gates — replaces SSM/linear-attn for local context |
| **Hardware-in-the-loop search** | Architecture search evaluated on real device latency/memory, not proxy metrics |
| **Minimal hybrid** | Conv (majority) + GQA (minority) — no SSM, no linear attention needed |
| **QK-Norm + RoPE** | Stabilizes GQA at small head dims (64) |
| **Pre-norm RMSNorm** | Training stability, no warmup needed |
| **Unified modality** | Same operators handle text, audio, video, time series, signals |
| **Featurization** | Input features modulate operator behavior (adaptive computation) |
| **Depth groups + weight sharing** | Parameter efficiency via targeted sharing (LFM1) |
| **MoE on hybrid backbone** | Sparse experts only in FFN; conv/GQA shared — 3–4B quality at 1.5B decode cost |

## 12. Open Questions / Research Directions

- [ ] **Operator-level ablation**: How much does each component (gated conv, GQA, QK-Norm, SwiGLU) contribute?
- [ ] **Scaling laws**: How does hybrid conv/GQA scale vs. pure attention vs. pure SSM beyond 3B?
- [ ] **Featurization design**: What input features best modulate conv gates for different modalities?
- [ ] **Training dynamics**: Do gated convs change loss landscape / optimization vs. attention?
- [ ] **Long-context extrapolation**: RoPE trained on 32K, config supports 128K — how well does it extrapolate?
- [ ] **MoE routing stability**: Adaptive biases vs. auxiliary loss — which generalizes better?
- [ ] **Quantization sensitivity**: Are gated convs more/less sensitive to INT4 than attention?
- [ ] **Cross-modal transfer**: Does shared operator design enable positive transfer text↔audio↔video?
